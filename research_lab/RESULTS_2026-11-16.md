# Puppy50 boot research evidence — 2026-11-16

These are experimental QEMU results, not a physical Acer test or a release.
The QEMU-only browser image in this test is a Debian Live research track;
the original kernel, compressed root and recovery image are preserved
relative to the authenticated v117 experimental base, not independently
established here as the original BookwormPup64 distribution.

## Matched 32 MiB versus 256 MiB prefetch

[Workflow run 43824576971](https://github.com/74127418528426leo-del/Test/actions/runs/43824576971),
job `compare (32)`, evidence artifact `14205848402` (SHA-256
`2c2738c913a27c620b042d00da3c45405f034e8f5962aa9729ebd474ca8760c6`).
The job ran five cold boots per condition on the same runner, three BIOS and
two UEFI, with 3072 MiB guest RAM. Each boot's serial record includes the
RAM copy-verification and ready markers; the benchmark reports media removal
and a subsequent browser HTTP 200 from the local fixture for all ten boots.
This is not independent reproduction on a second runner.

| BIOS 1 | 8.272 | 9.270 |

| BIOS 2 | 8.271 | 8.273 |
| UEFI 2 | 13.132 | 13.157 |

Times in this table are host-monotonic upper observations of the rendered
home-page detector, rounded here to milliseconds. They are not exact first
Firefox paint times. The candidate was approximately 0.209 s slower on this
sample; the median interval between screenshot-probe starts was about
0.213 s, so this is not convincing evidence of a speed difference.

Both conditions use Firefox priority -10 and Zstd level 3. The control ISO
SHA-256 was `2d70cc81a683e583e15faf5e47dab4677a1986fca2a8beed31b8a574bbbae53f`;
the candidate was `917a40ec843144fdcdd55746a74925e9445a479b2bd074ba968f16d7c7fc17aa`.
The fixture establishes the recorded local HTTP request, not broad site
compatibility or a guest CA-verification result. The benchmark reported
`guest_ca_https_probe: false`; screenshots require independent visual review.

## Critical path and measurement caveats

In all ten boots the guest timestamps put the interval from entry into the
early X11 launcher until its existing `mcookie` call returned at 1.00–1.02 s.
The reason for the duration is not established. In these same samples the
host first observed the early-user marker at a median 2.883 s for BIOS and
7.517 s for UEFI. This locates a large firmware-dependent difference before
the early-user marker; it does not separate firmware from bootloader or
kernel startup. The interval between host receipt of the Firefox execution
marker and host observation of the rendered home page was approximately
3.88–4.52 s, including observation delays. These are host-to-host
measurements; guest uptime is never subtracted from host monotonic time.

The earlier matched run `43777265230` reported four UEFI home detections of
13.55 s. Its serial logs and first-home screenshots differ across boots, and
the benchmark has no 13.55-second timeout. Its 0.2-second screenshot
polling and two-decimal rounding can produce repeated values. The older
artifact lacks per-probe timestamps, so the precise reason for the equality
cannot be recovered retrospectively.

## Failed and pending work

- In job `compare (0)` of run `43824576971`, the first candidate BIOS boot
  reached the browser and post-eject fixture, but its matched control did not
  produce the required browser HTTP 200 after three attempts. The job stopped;
  there is no valid five-pair zero-prefetch comparison from that job.
- The first parallel-cookie experiment,
  [run 43825819475](https://github.com/74127418528426leo-del/Test/actions/runs/43825819475),
  failed its first BIOS boot: the background task started but no cookie-ready
  or Xorg marker appeared, and no home frame was detected within 100 s.
  Media was not removed and post-eject networking was not tested.
- A revised isolated experiment changes the background task to use paths
  inside the guest root. Its outcome is tracked separately; the failure above
  remains part of the history.
- Two separate runs must verify the exact same ISO SHA-256 before the VM goal
  is reported verified. The current scheduler rebuilds rather than retaining
  and replaying the exact candidate bytes; therefore this gate is fail-closed
  and automated exact-ISO replay is still an open engineering task.

The under-five-second VM target, physical Acer behavior, and 384 MiB
RAM-only Firefox target are not verified.
